# CLAUDE.md: goals-to-actions-api

The API for Goals to Actions. Product context, rules and ADRs live in the parent folder (`../CLAUDE.md`, `../docs/`). Read `../docs/data-model.md` before any schema or query work, and `../docs/product-rules.md` before planner work.

## Stack

Python 3.15, FastAPI, Pydantic. Packages and the virtualenv are managed by uv (`pyproject.toml`, `uv.lock`, `.python-version`).

Data (ADR-007):

- Postgres 18, run locally with `podman compose` (`compose.yaml`).
- Migrations as plain SQL files with up and down, run by dbmate through `bin/dbmate`.
- Queries as `.sql` files; sqlc generates the Python (`sqlc.yaml`, plugin `sqlc-gen-python`). No ORM. SQLAlchemy is used only as the connection the generated code runs through, on psycopg 3.

The README has the commands.

## Structure

```
app/
  config.py      APP_NAME (the only place the product name appears in code), DATABASE_URL, FIXED_USER_ID
  schemas.py     ApiModel, the base for everything the API sends or accepts
  database.py    Database: transaction(user_id, action) and read(); the get_database and current_user_id dependencies
  db/            generated by sqlc: never edit, regenerate with `sqlc generate`
  main.py        the FastAPI app and its routes
bin/dbmate       dbmate in its container; `--test` for the test database
db/
  migrations/    one SQL file per change, up and down; sqlc's schema too
  queries/       one .sql file per table, the queries sqlc generates from
  schema.sql     written by bin/dbmate; committed, never edited
tests/           conftest.py gives tests a rolled-back connection to the test database
specs/           the map of the API work (specs/README.md) and one spec per slice
tasks/           the plan and task list for the slice being built
```

Work is built slice by slice from `specs/`. A spec is a draft until its plan is written; read the map's shared decisions and conventions before starting a slice.

## Adding a table

In the migration that creates it:

- The shared columns: `id uuid primary key` (made on the device), `user_id` (the owner, in every foreign key), `created_at` and `updated_at` (`timestamptz not null default now()`), `deleted_at timestamptz`.
- Status and type columns as text with a check, not enum types.
- Two triggers: `before update ... execute function set_updated_at()` and `after insert or update or delete ... execute function audit()`.
- Reads leave out deleted rows (`deleted_at is null`) from the start.

Then: `bin/dbmate up`, `bin/dbmate --test up`, the queries in `db/queries/<table>.sql`, `sqlc generate`, and tests. Commit the migration, `db/schema.sql` and `app/db/` together.

## Rules

- **The OpenAPI schema is the contract.** The front end generates its types from it, so every route declares its request and response models.
- **JSON is camelCase, Python is snake_case.** Every API model extends `ApiModel`, which does the aliasing. Don't alias fields by hand. `tests/test_contract.py` fails if a snake_case property reaches the schema.
- **An operation is named after its route function,** in camelCase (`check_off_task` becomes `checkOffTask`), because generated clients take their function names from it. Give route functions the name the front end should call.
- **Ask before adding a dependency.**
- **Days, moments and times are stored three ways** (`date`, `timestamptz` in UTC, `time`), never with an offset. See `../docs/data-model.md`.
- **History:** if a feature reads it, it's a table or column; everything else is the audit log (ADR-005). Nothing reads the audit log.
- **Application code writes only inside `database.transaction(user_id, action)`,** which tells the audit trigger who did what. Reads use `database.read()`, which Postgres keeps read-only. Neither holds SQL: queries live in `db/queries/` and are called through the generated `app/db/`.
- Write or update tests with every behavior change. Tests that touch the database run against real Postgres, never SQLite. They use the `database` or `connection` fixture, whose writes are rolled back.
- Update `../docs/` in the same piece of work when behavior or the data model changes.

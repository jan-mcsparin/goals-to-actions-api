# CLAUDE.md: goals-to-actions-api

The API for Goals to Actions. Product context, rules and ADRs live in the parent folder (`../CLAUDE.md`, `../docs/`). Read `../docs/data-model.md` before any schema or query work, and `../docs/product-rules.md` before planner work.

## Stack

Python 3.15, FastAPI, Pydantic. Packages and the virtualenv are managed by uv (`pyproject.toml`, `uv.lock`, `.python-version`).

Data (ADR-007):

- Postgres 18, run locally with `podman compose` (`compose.yaml`).
- Migrations as plain SQL files with up and down, run by dbmate through `bin/dbmate`.
- Queries as `.sql` files; sqlc generates the Python (`sqlc.yaml`, plugin `sqlc-gen-python`). No ORM. SQLAlchemy is used only as the connection the generated code runs through, on psycopg 3.

The README has the commands.

## Structure

```

  schemas.py     ApiModel, the base for everything the API sends or accepts; the error shape
  database.py    Database: transaction(user_id, action) and read(); the get_database dependency
  dependencies.py  CurrentDatabase and CurrentUserId, what routes ask for
  errors.py      NotFound and NotAllowed, raised by rules and routes; main.py sends them as 404 and 409
  time_zone.py   clock and Now: the moment where the phone is, from the X-Time-Zone header (tests pin the clock)

  users.py       lock_user: the user lock every planning or numbering write takes first
  weeks.py       week_of (a week is named by its Monday), current_week, target_week and open_weeks (the current week, and next week once open)
  turnover/      due.py (pure: what a week is due, how a task ends), rework.py (pure: an edited item's week), endings.py, rules.py (catch_up, open and close a week, wrap_up), dependencies.py (Today, which brings the weeks up to date and keeps the phone's time zone), routes.py (wrapUpWeek)

  openapi.py     writes openapi.json
  db/            generated by sqlc, one module per table: never edit, regenerate with `sqlc generate`
  main.py        the FastAPI app; serves health, the sign-in routes and, behind a session, each slice's router under /api
  <slice>/       one folder per slice (aspirations/, goals/, milestones/, quitting/, recurring_items/, settings/, tasks/):
    routes.py      the router. Thin: validate, open a transaction, call queries or rules, return an ApiModel
    models.py      request and response models
    rules.py       writes that need more than one query; takes the connection, no FastAPI imports
    page.py        milestones/ only: the goal's page, which getGoal and every milestone write return
    week.py        tasks/ only: the week read, and the task as every task write returns it
    progress.py    tasks/ only: what goal reads count from tasks (this week's progress, a one-off goal's steps)
    record.py      quitting/ only: a quitting goal's days and run, for its writes, its page and the week read
bin/dbmate       dbmate in its container; `--test` for the test database
db/
  migrations/    one SQL file per change, up and down; sqlc's schema too
  queries/       one .sql file per table, the queries sqlc generates from
  schema.sql     written by bin/dbmate; committed, never edited
openapi.json     the contract, written by `uv run python -m app.openapi`; committed, never edited
tests/           conftest.py gives tests a rolled-back connection to the test database, a clock pinned to Wed 18 Nov 2026 (`fixed_clock` moves it), and a `client` signed in as the fixed user from the app's origin

tasks/           the plan and task list for the slice being built
```

Work is built slice by slice from `specs/`. A spec is a draft until its plan is written; read the map's shared decisions and conventions before starting a slice.

## Adding a table

In the migration that creates it:

- The shared columns: `id uuid primary key` (made on the device), `user_id` (the owner, in every foreign key), `created_at` and `updated_at` (`timestamptz not null default now()`), `deleted_at timestamptz`.
- Status and type columns as text with a check, not enum types.
- Two triggers: `before update ... execute function set_updated_at()` and `after insert or update or delete ... execute function audit()`.
- Reads leave out deleted rows (`deleted_at is null`) from the start.

A rule checked at commit (a constraint trigger `deferrable initially deferred`) is also named in `CHECK_AS_AT_COMMIT` in `app/database.py`, since tests never commit.

Then: `bin/dbmate up`, `bin/dbmate --test up`, the queries in `db/queries/<table>.sql`, `sqlc generate`, and tests. Commit the migration, `db/schema.sql` and `app/db/` together.

## Adding a route

- It goes in its slice's `routes.py`, named for what the front end calls (`retire_aspiration`). `main.py` includes the router under `/api`, so its prefix is `/goals`, not `/api/goals`; a contract test fails for any route outside `/api`.
- `main.py` includes a slice's router in `signed_in`, so every route answers 401 without a session; `tests/test_signed_out.py` reads the schema and fails for one that doesn't. Only the sign-in routes and `health` are outside it.
- Creates are `PUT /things/{id}` with the id made on the device; actions are `POST /things/{id}/action`; deletes are `DELETE /things/{id}`. All are written so that sending them twice changes nothing more (`specs/README.md`, decisions 6 and 7). A delete sets `deleted_at` on the row and on what goes with it, and empties links to it from rows that stay (`specs/delete.md`).
- Request and response models are hand-written in `models.py` and extend `ApiModel`. Generated row models (`app/db/models.py`) never leave the API; a response model has a `from_row`.
- A write that takes several queries is a function in `rules.py` that runs inside the route's transaction. It raises `NotFound` or `NotAllowed("why")`; the route declares them with `responses=NOT_FOUND` or `NOT_ALLOWED`.
- A write that renumbers a user's rows, and every goal, milestone and check-in write, calls `lock_user` (`app/users.py`) first, so two arriving together run in turn.
- A route that needs the day asks for `Today` (from `app/turnover/dependencies.py`), which also opens and closes weeks that are due.
- Every text field a request can set has a longest length and `NoNul` (`app/schemas.py`): Postgres text can't hold a NUL character, and without it the request ends in a 500.
- Every 422 has FastAPI's list shape. A check written by hand raises `RequestValidationError`, as `app/time_zone.py` does.
- Tests go through the `client` fixture: the ordinary case, each rule, another user's row, the same write twice, and the audit action. Every write also needs a case in `tests/test_repeats.py`, and every read a case in `tests/test_other_user.py`; each fails without one. A write that takes the user lock gets a line in a lock test in `tests/test_user_lock.py`.
- Then `uv run python -m app.openapi`, and commit `openapi.json` with the change.

## Rules

- **The OpenAPI schema is the contract.** The front end generates its types from it, so every route declares its request and response models.
- **JSON is camelCase, Python is snake_case.** Every API model extends `ApiModel`, which does the aliasing. Don't alias fields by hand. `tests/test_contract.py` fails if a snake_case property reaches the schema.
- **An operation is named after its route function,** in camelCase (`check_off_task` becomes `checkOffTask`), because generated clients take their function names from it. Give route functions the name the front end should call.
- **Ask before adding a dependency.**
- **Days, moments and times are stored three ways** (`date`, `timestamptz` in UTC, `time`), never with an offset. See `../docs/data-model.md`.
- **History:** if a feature reads it, it's a table or column; everything else is the audit log (ADR-005). Nothing reads the audit log.
- **Application code writes only inside `database.transaction(user_id, action)`,** which tells the audit trigger who did what. Reads use `database.read()`, which Postgres keeps read-only. Neither holds SQL: queries live in `db/queries/` and are called through the generated `app/db/`.
- Write or update tests with every behavior change. Tests that touch the database run against real Postgres, never SQLite. They use the `database` or `connection` fixture, whose writes are rolled back.
- Update `../docs/` in the same piece of work when behavior or the data model changes.
